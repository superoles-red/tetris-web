# tools/ppu — дифференциальная проверка PPU против JSNES 2.1.0

Dev-only инструменты для проверки `src/nes/ppu.js`. В сайт/сборку не входят.
JSNES 2.1.0 — `devDependency` (Apache-2.0), используется только как
поведенческий эталон (`THIRD_PARTY_NOTICES.md`). В репозитории нет ни ROM, ни
дампов CHR/PRG, ни скриншотов игры — только хэши кадров и метаданные.

## Запуск

```bash
# по умолчанию: оба известных дампа по абсолютным путям, 220 кадров,
# 11 контрольных кадров, ROM ищется в соседнем каталоге tetris-dendy-web
node tools/ppu/diff-jsnes.mjs

# свои параметры
node tools/ppu/diff-jsnes.mjs --frames 320 --check 10,20,65,193,240,280 --json

# один ROM
node tools/ppu/diff-jsnes.mjs --rom "/абсолютный/путь/game.nes"
```

Без ROM (CI) инструмент печатает `ROM не найден … пропущен` и выходит с кодом 0.
Без установленного `jsnes` — то же. Те же проверки входят в
`tests/ppu.test.mjs` (дифференциальный тест пропускается без ROM).

## Что именно сравнивается

Для каждого контрольного кадра N:

1. JSNES прогоняет реальный ROM (сценарий ввода: START/A каждые 30 кадров
   после 60-го — так игра доходит от загрузки до геймплея), затем снимается
   состояние PPU `jsnes.ppu.toJSON()` и эталонный `buffer`.
2. Состояние переводится в формат нашего PPU (`adaptJsnesState`: та же
   нумерация строк, но физическая NTSC — у JSNES внутренняя, `(scanline+241)%262`)
   и применяется через `ppu.fromJSON()`.
3. Два независимых пути нашего PPU:
   - `renderFullFrame()` — полный рендер кадра из состояния без CPU (пауза);
   - `startFrame()` + `advanceDots(341*262+2)` — обычный путь `console.js`.
4. Оба буфера сравниваются с эталоном побайтово (`Uint32Array(256*240)`).

Кадры выбраны стабильные: загрузка/титул/меню/геймплей, где посреди кадра нет
изменений палитры/скролла (Tetris меняет их только в vblank).

### Про mapper 148

`game.nes` — mapper 148 (Tengen), которого нет в JSNES 2.1.0. Для эталона
копия ROM в памяти помечается в iNES-заголовке как mapper 0 (файл на диске не
меняется). Для PPU-сравнения это безопасно: PRG фиксирован (32 КиБ), а
переключение CHR-банков влияет только на то, что попало в CHR-окно у JSNES;
состояние всё равно снимается с JSNES и применяется к нашему PPU. `game-ru.nes`
(mapper 3, CNROM) JSNES грузит нативно.

## Результаты (27.11.2026, macOS, Node 24.16)

Сценарий: `START`/`A` каждые 30 кадров, 320 кадров, ROM en+ru.

| ROM (sha256, первые 12) | кадры | расхождений `renderFullFrame` | расхождений `advanceDots` |
|---|---|---|---|
| `game.nes` `53970a2b2581` | 10,20,40,65,73,102,132,162,193,201,210,240,280 | 0 | 0 |
| `game-ru.nes` `33f04ac3953e` | 10,20,40,65,73,102,132,162,193,201,210,240,280 | 0 | 0 |

Дополнительные прогоны (тем же сценарием, проверка каждого кадра):

| диапазон | en | ru |
|---|---|---|
| кадры 1–190, шаг 2 | 95 проверок, 1 расхождение (кадр 71 — переходный) | то же |
| кадры 180–400, шаг 4 | 56 проверок, 0 расхождений | 56, 0 |
| кадры 402–900, шаг 6 | 84 проверки, 0 расхождений | 84, 0 |

Кадр 71 — момент переключения экрана: рендер включается/выключается посреди
кадра, палитра/скролл меняются не в vblank. Такие кадры не воспроизводятся
из финального состояния PPU даже самим JSNES (проверено: его собственный
`fromJSON` + перерисовка даёт те же 1965 расхождений в пикселях). Это не
дефект нашего PPU: стабильные кадры до и после сходятся побайтово.

Итог: на всех стабильных проверенных кадрах (≈250 точек на каждый дамп,
загрузка → титул → меню → геймплей) кадр нашего PPU совпадает с JSNES
побайтово, включая `buffer`, `imgPalette/sprPalette`, левый кроп и палитровые
эффекты.

## JSNES-особенности, воспроизведённые намеренно

Композитор старого порта (`compositor.js`) и раскладка HUD измерены по кадрам
JSNES, поэтому для побайтового совпадения повторены и его странности:

1. **Строка 0 при непрозрачном BG зануляется на vblank.** В JSNES строка 0
   рисуется напрямую в `buffer`, а ленивая композиция копирует в неё
   незаполненный `bgbuffer[0]` (нули). Настоящее железо показывает строку 0
   нормально; мы повторяем эталон (иначе русский титул отличался бы на 192 px).
2. **Правые `FH` пикселей строки при fine X > 0 остаются фоном** — JSNES
   рисует только 32 тайла без префетча следующего.
3. **Верхние `8-regFV` строк не рисуются при fine Y > 0** — JSNES-условие
   `scan >= cntFV`.
4. **Кроп 8 пикселей по краям** (левый/`clipToTvSize`) применяется ко всему
   кадру после рендера, а не во время — так же, как в JSNES `endFrame()`.

## Известные отклонения/упрощения (документированы в `src/nes/ppu.js`)

- Рендер строки — в момент её начала (контракт §3.3), JSNES композитит лениво.
  При изменениях палитры/скролла только в vblank результат идентичен.
- Спрайты строки 1 берутся из текущей OAM, а не из «залипшей» secondary OAM
  JSNES; строка 0 спрайтов не содержит по геометрии (Y≥0 ⇒ экранная строка ≥1).
  Для Tetris спрайтов на строках 0–1 нет.
- Sprite overflow — честный перебор OAM (до 8 в строке), без аппаратного бага
  «диагонального» чтения при переполнении. На буфер не влияет.
- 8×16 спрайты реализованы по железу. У JSNES 2.1.0 в `renderSpritesPartially`
  для 8×16 есть сдвиг индекса тайла на -1 в pattern table 1 — этот баг не
  воспроизводится. Tetris 8×16 не использует (проверено: `f_spriteSize === 0`
  во всех просмотренных кадрах).
- Запись в OAM во время рендера не подавляется, OAM corruption не
  эмулируется: игры пишут OAM в vblank/DMA.
- Sprite 0 hit по времени — в начале строки (не на конкретном dot). Tetris его
  не использует для синхронизации (флаг проверяется тестами).
- `$2006` берёт 2 бита fine Y из старшего байта — как vNES/JSNES; для адресов
  `$0000-$3FFF` это эквивалентно железу (Tetris других адресов не пишет).
- Открытая шина PPU: значение хранится и возвращается, но не «затухает» по
  кадрам (в Tetris значение младших бит $2002 не влияет на игру).

## Интеграция (важно для console.js/engine.js)

- `ppu.clipToTvSize` по умолчанию `true` (как в JSNES). Игровой движок должен
  выставить `ppu.clipToTvSize = false` сразу после создания/сброса консоли
  (старый `engine.js` делал именно это) — иначе `buffer` обрезан по 8 px
  сверху/снизу/справа, и раскладка `compositor.js` поедет.
- `frameEnded` выставляется на строке 241 (vblank), `console.js` сбрасывает его
  сам; `startFrame()` тоже сбрасывает его и заливает буфер фоном.
- `$2002` снимает только vblank, но не `nmiPending`: NMI «защёлкивается» и
  снимается консолью при приёме прерывания (`console.js` так и делает).
- Запись в CHR через `$2007`: PPU пишет CHR RAM, если `ppu.chrWritable = true`
  или задан `ppu.onChrWrite = (addr, value) => mapper.writeChr(addr, value)`.
  Для Tetris (CHR ROM) запись игнорируется — как на железе. Окно CHR от маппера
  приходит через `ppu.setChrWindow(bytes8k)` (уже подключено в `console.js`).
- `ppu.oamDma(cpuMem, page)` копирует 256 байт в OAM с переносом от OAMADDR;
  `console.js` пока копирует `spriteMem` напрямую (для Tetris OAMADDR=0 —
  эквивалентно).
- Снапшоты: `ppu.toJSON()` не хранит `ptTile` (передекодируется из `vramMem`),
  зато хранит `buffer`, палитры, счётчики скролла, тайминги и флаги статуса.
  `fromJSON()` принимает и старые/чужие состояния — недостающие поля берутся
  из текущего состояния, палитры при отсутствии пересчитываются.
